# **Anthropic’s Engineering Postmortem: When AI Bugs Hit Claude’s Responses**  

Over the past month, Anthropic users reported weird behavior from Claude—sudden nonsense code, Thai characters in English answers, and inconsistent response quality. Turns out, three sneaky infrastructure bugs were to blame. Here’s what went wrong, how it was fixed, and what Anthropic is doing to avoid a repeat.  

### **The Culprits: Three Silent Killers of AI Quality**  

1️⃣ **The Context Window Mix-Up (Aug 5 - Sep 16)**  
   - Some requests for **Sonnet 4** (one of Claude’s models) were mistakenly routed to servers prepped for a **_1 million token context window_**—even when users only asked for short responses.  
   - At its worst, **16% of Sonnet 4 requests were affected**, with sticky sessions compounding the problem (once you hit a bad server, later queries did too).  
   - **Fix?** Better routing logic, fully deployed by Sep 16.  

2️⃣ **The Output Corruption Bug (Aug 25 - Sep 2)**  
   - A botched optimization led to **random gibberish**—like Thai script ("สวัสดี") popping up in English responses or broken code snippets.  
   - Mostly impacted **Opus 4.1, Opus 4, and Sonnet 4** on the Claude API, but spared third-party platforms.  
   - **Fix?** Reverted the change and added tests for bizarre token outputs.  

3️⃣ **The XLA:TPU Compiler Fiasco (Aug 25 - Sep 12)**  
   - A new token-selection tweak triggered a **latent bug in Google’s XLA:TPU compiler**, mainly affecting **Haiku 3.5** but possibly **Sonnet 4** and **Opus 3**.  
   - **Fix?** Rolled back for Haiku (Sep 4) and later for Opus (Sep 12).  

### **Why Detection Took So Long**  
- **The bugs overlapped**, making root cause analysis messy.  
- **Uneven impact**: Some users noticed degraded responses while others didn’t, leading to contradictory reports.  
- **Sticky routing** meant some unlucky users got hit repeatedly.  

### **What’s Changing at Anthropic?**  
✅ **Expanded monitoring**—now tracking unexpected outputs (e.g., random Unicode)  
✅ **More cautious load balancing changes**  
✅ **Better validation across hardware** (AWS Trainium, NVIDIA GPUs, TPUs)  

**The Big Lesson:** Even AI companies **aren’t immune to mundane infrastructure bugs**—but transparency helps rebuild trust.

# **Intel Engineers Supercharge ClickHouse for 200+ Core Servers**  

### **How Intel is rewriting the rules for ultra-high core count database performance**  

Modern CPUs are pushing core counts into uncharted territory—Intel’s latest Granite Rapids and Sierra Forest processors boast up to **288 cores per socket**, with multi-socket systems exceeding 400 cores. But more cores don’t always mean more performance—especially for databases like **ClickHouse**, where bottlenecks like **lock contention, cache coherence, and NUMA effects** can cripple scalability.  

A team of Intel engineers has spent **three years** systematically optimizing ClickHouse for these massive core counts, delivering **10x speedups on some queries** and consistent performance boosts across the board. Here’s how they did it.  

## **The Challenge of Ultra-High Core Counts**  
The end of **Dennard scaling** (the era when transistors became faster *and* more efficient) forced chip designers to prioritize **more cores over faster cores**. But for analytics workloads, unlocking the full potential of 200+ cores isn’t easy. The biggest hurdles?  

- **Lock contention**: A single mutex can cause quadratic slowdowns—switching from 8 to 80 cores can **100x wait times** due to Amdahl’s Law.  
- **Cache coherence overhead**: Every cache line bounce wastes precious CPU cycles.  
- **Memory bandwidth saturation**: Simply feeding all those cores with data is a challenge.  
- **NUMA effects**: Remote memory access on multi-socket systems introduces latency spikes.  

Intel’s tests on **Granite Rapids (240 cores), Sierra Forest (288 cores), and Sapphire Rapids (128 cores x2)** revealed that **small inefficiencies become catastrophic at scale**.  

## **The Fixes: 5 Key Optimizations**  

### **1. Slaying Lock Contention With Smarter Caching**
**Problem:** The `QueryConditionCache` (which speeds up WHERE clause filtering) used **exclusive locking**, creating brutal contention. At 240 cores, **76% of CPU time was wasted in spinlocks**.  

**Solution:** Intel replaced the **coarse-grained mutex** with **fine-grained synchronization**, reducing lock duration and switching to **shared locks for reads**. Result? A massive reduction in thread stalls.  

### **2. Cutting NUMA Bottlenecks**  
Multi-socket systems suffer when threads access **remote memory nodes**. The team optimized **thread placement and memory affinity**, keeping cores on the same NUMA node when possible—slashing latency.  

### **3. Memory Bandwidth Optimization**
With so many cores fighting for RAM, **efficient caching** was critical. By improving **data locality and pre-fetching**, Intel reduced stalls from memory starvation.  

### **4. Thread Coordination Overhaul**
At hundreds of threads, even **minor synchronization costs** add up. The team rewrote scheduling logic to **minimize cross-core coordination**, reducing thread thrashing.  

### **5. Hardware-Aware Query Execution**
Intel’s engineers tuned ClickHouse to **detect available cores and allocate workloads more intelligently**, ensuring full utilization without overwhelming shared resources.  

## **Results: 10x Faster Queries & Real-World Impact**  
Through **perf, VTune, and custom profiling**, each optimization delivered **2-10% gains in aggregate**. Some individual queries saw **10x speedups**—proving ClickHouse **can scale efficiently** even on **behemoth core counts**.  

Best of all? **All these optimizations are now merged into mainline ClickHouse**, benefiting users worldwide.  

### **What’s Next?**  
With **future Intel CPUs pushing past 300 cores**, the hunt for scalability bottlenecks continues. The battle between hardware and database optimization is far from over—but ClickHouse is now **ahead of the curve**.

### The Asus gaming laptop ACPI firmware bug

# ASUS ROG Laptop Users Beware: BIOS-Level Bug Causes Infuriating Performance Issues  

### The Problem That Defies Standard Fixes  
Many ASUS ROG (Republic of Gamers) laptop owners—particularly those with Strix, Scar, or Zephyrus models—have reported bizarre system stutters, audio crackling, and mouse freezes. Despite having top-tier specs (RTX 30/40 GPUs, Intel Core i9 CPUs, ample RAM), these high-end machines struggle with basic real-time tasks like video playback and Discord calls.  

Users have tried everything:  
- Updating drivers (multiple times)  
- Clean Windows reinstalls  
- Disabling power-saving features  
- Adjusting processor settings  
- Even switching to *Linux* (where the issue **still persists**)  

The real culprit? A **firmware-level bug in the BIOS**, specifically in the ACPI (Advanced Configuration and Power Interface) subsystem.  

### LatencyMon Reveals the Smoking Gun  
Running [LatencyMon](https://www.resplendence.com/latencymon) (a tool to measure system responsiveness) exposes severe **interrupt and DPC (Deferred Procedure Call) latency**:  

- **Highest interrupt-to-process latency: 65,816.60μs** (a normal system should stay under 500μs)  
- **Worst offender?** The **ACPI.sys** driver, a critical Windows component that executes BIOS-provided ACPI Machine Language (AML).  
- The issue is **CPU 0-bound**—almost all DPCs bottleneck on a single core.  

This isn’t a Windows or driver problem—**the firmware is feeding ACPI.sys inefficient code that tanks performance**.  

### Digging Deeper: ETW Tracing Confirms the Issue  
To trace the root cause, an **Event Tracing for Windows (ETW) analysis** was performed, revealing:  
- **Periodic latency spikes every 30-60 seconds**—highly unusual, suggesting an embedded timer or scheduled firmware event going rogue.  
- **Frequent, unnecessary GPU power cycling**—the system keeps toggling the discrete GPU (_SB.PC00.GFX0._PS0) on and off, even when it should stay powered.  

### Why This Matters  
- **Gaming laptops should excel at real-time tasks**, but this bug cripples responsiveness.  
- **Power management logic in the BIOS is misbehaving**, likely due to poorly optimized AML code.  
- **No simple fix exists**—this requires ASUS to release a **firmware update**.  

### What You Can Do  
- **Monitor ASUS updates**: Check for BIOS revisions addressing ACPI-related issues.  
- **Disable dynamic GPU switching**: If possible, lock the dGPU in "Always On" mode.  
- **Raise awareness**: The more ASUS users report this, the higher the chance of a fix.  

📌 **Conclusion**: If your high-end ASUS laptop stutters for no apparent reason, blame the BIOS—not Windows. Until ASUS releases a patch, expect frustration.
