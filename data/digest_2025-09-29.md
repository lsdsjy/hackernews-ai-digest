### Safe zero-copy operations in C#

# **C# Power Moves: Low-Level Performance Without the Danger**  

### **C# Can Go Where Java Can’t**  
C# is more than just a Java-like language—it lets you write high-level, abstracted code *and* dive into low-level, unsafe optimizations when needed. Unlike Java, C# supports *pointers*, letting you bypass garbage collection for speed-critical or system-level tasks.  

### **Bounds-Checking and Performance**  
By default, C# checks array bounds for safety, which can slow things down. For example, this loop:  

```csharp  
int Sum(int[] array)  
{  
    int sum = 0;  
    for (int i = 0; i < array.Length; i++)  
        sum += array[i];  
    return sum;  
}  
```  

is optimized well—**zero bounds checks** in the compiled assembly. But tweak the function slightly:  

```csharp  
int Sum(int[] array, int start, int end)  
{  
    int sum = 0;  
    for (int i = start; i <= end; i++)  
        sum += array[i];  
    return sum;  
}  
```  

Now, the compiler can’t be sure if `start` and `end` are safe, so it adds **costly bounds checks**.  

### **Danger Zone: Unsafe Pointers**  
If you truly need speed, C# lets you use **raw pointers** like in C:  

```csharp  
unsafe int Sum(int* ptr, int length)  
{  
    int* end = ptr + length;  
    int sum = 0;  
    for (; ptr < end; ptr++)  
        sum += *ptr;  
    return sum;  
}  
```  

This compiles to **lean, bounds-check-free** assembly. **But be warned:**  
- **No runtime safety nets** → buffer overflows, crashes, or security bugs if misused.  
- Forces callers to use `unsafe` code.  

### **The Best of Both Worlds: Span<T>**  
Instead of raw pointers, C# offers `Span<T>`, a *safe* way to work with array slices efficiently:  

```csharp  
readonly ref struct Span<T>  
{  
    readonly ref T _ptr;  // Stack-only reference  
    readonly int _len;  
}  
```  

**Why it’s awesome:**  
✅ **Zero-cost bounds checks** (compiler guarantees safety)  
✅ **Works with arrays, stack memory, and unmanaged memory**  
✅ **No risk of dangling pointers** (lifetime tied to the stack)  

### **Key Takeaway**  
C# gives you **fine control over performance and safety**:  
🔹 **Prefer `Span<T>` for high-performance slices without the danger of pointers**  
🔹 **Use `unsafe` code sparingly—only when you *really* need that extra edge**  

Want raw speed **without** segfaults? `Span<T>` is your best friend! 🚀

### A SQL Heuristic: ORs Are Expensive

#### [Submission URL](https://ethanseal.com/articles/ors-are-expensive) | 151 points | by [ethanseal](https://news.ycombinator.com/user?id=ethanseal) | [69 comments](https://news.ycombinator.com/item?id=45413525)

# **Why OR Clauses Slow Down Your SQL Queries (And What to Do Instead)**  

SQL queries with `OR` conditions can be **100x slower** than equivalent queries rewritten using `AND`, unions, or table redesigns—even with proper indexing. Here’s why ORs are so expensive and how to avoid them.  

## **The Problem: ORs Are Slow with Indexes**  

Imagine a query counting applications where a user is either the submitter or reviewer:  
```sql  
SELECT COUNT(*) FROM application  
WHERE submitter_id = :user_id OR reviewer_id = :user_id;  
```  
With 1M rows and uniform distribution, this takes **>100ms**, even with indexes. Why?  

### **The Fix: Rewrite with ANDs + UNION Logic**  
This optimized version does the same in **<1ms (100x faster!)** by avoiding ORs:  
```sql  
SELECT  
  (SELECT COUNT(*) FROM application WHERE reviewer_id = :user_id) +  
  (SELECT COUNT(*) FROM application WHERE submitter_id = :user_id) -  
  (SELECT COUNT(*) FROM application WHERE submitter_id = :user_id AND reviewer_id = :user_id);  
```  

## **Why ORs Are So Expensive**  

1. **Indexes Don’t Help Much**  
   - For `WHERE A OR B`, the database **either**:
     - Does two separate index lookups and merges them (costly for large datasets), or  
     - Scans the entire table (slowest).  
   - `AND` queries, in contrast, use selectivity stats to pick the best index.  

2. **Unions Increase Data Volume**  
   - `AND` shrinks the result set—OR **expands** it, forcing extra work.  

3. **Modern DBs Focus on AND Optimizations**  
   - Most filters (e.g., faceted search) use `AND`, so query planners prioritize them.  

## **Better Structural Solutions**  

### **1. Use a Junction Table Instead of Multiple FKs**  
Instead of:  
```sql  
CREATE TABLE application (  
  submitter_id INT8 NOT NULL,  
  reviewer_id INT8 NOT NULL  
);  
```  
Do this:  
```sql  
CREATE TABLE application_user (  
  user_id INT8 NOT NULL,  
  application_id INT8 NOT NULL,  
  user_type ENUM('submitter', 'reviewer') NOT NULL  
);  
```  
Now, queries on `user_id` are **always fast**, no ORs needed:  
```sql  
SELECT * FROM application a  
JOIN application_user au ON a.id = au.application_id  
WHERE au.user_id = :user_id;  
```  

### **2. Avoid Multi-Table Inheritance (Use a Base Table)**  
Instead of two tables like:  
```sql  
CREATE TABLE post (user_id INT8, title TEXT);  
CREATE TABLE comment (user_id INT8, body TEXT);  
```  
Use inheritance:  
```sql  
CREATE TABLE writing (writing_id INT8, user_id INT8, body TEXT);  
CREATE TABLE post (writing_id INT8, title TEXT);  
```  
Now all user-written content is **indexed once**, avoiding UNIONs.  

## **Key Takeaway**  
**ORs are slow—avoid them by:**  
✅ Rewriting with `AND` / `UNION`  
✅ Using junction tables for multi-FK relationships  
✅ Structuring data inheritance properly  

Want to dive deeper? Check out analysis on **query planning and indexing strategies**. 🚀

### **Discussion Summary: Why OR Clauses Slow Down SQL Queries**  

The discussion expands on why `OR` clauses are inefficient in SQL and explores alternatives, optimizations, and database-specific behaviors.

#### **Key Themes:**  

1. **Rewriting ORs for Performance**  
   - Several users highlight that rewriting `OR` conditions as `UNION`, `AND`, or separate queries often performs better due to optimizer limitations.  
   - Example:  
     ```sql  
     -- Slow:  
     SELECT * FROM table WHERE a = 1 OR b = 2;  
     -- Fast alternative:  
     SELECT * FROM table WHERE a = 1  
     UNION  
     SELECT * FROM table WHERE b = 2;  
     ```  
   - **Caution**: `UNION` can introduce duplicates, so `UNION ALL` or `DISTINCT` may be needed.  

2. **Database-Specific Optimizations**  
   - **PostgreSQL** handles `OR` with `BitmapOr` scans (Postgres 17+), but performance varies. Running `EXPLAIN ANALYZE` helps verify the plan.  
   - **SQLite** automatically rewrites `OR` as `UNION` in some cases.  
   - **MSSQL/Sybase** users report mixed results, with manual query rewriting sometimes necessary.  

3. **Indexing Strategies**  
   - B-tree indexes struggle with `OR` conditions across columns.  
   - **Skip Scans** (PostgreSQL 18+, other databases) help efficiently scan compound indexes, but not all engines support this.  
   - **Junction Tables** (for many-to-many relationships) simplify query patterns and avoid `OR`s entirely.  

4. **Optimizer Challenges**  
   - Query planners rely on statistics and heuristics, which can misjudge `OR` selectivity.  
   - Complex subqueries or joins may force sequential scans instead of index use.  

5. **Alternative Approaches**  
   - **Denormalization** (e.g., Elasticsearch) can outperform SQL for search-heavy workflows.  
   - **Query Plan Hints** (explicitly suggesting indexes) help in some cases but require deep tuning.  

6. **LLMs for Optimization?**  
   - Some users suggest using LLMs (e.g., ChatGPT) to review slow queries, though manual validation remains critical.  

#### **Notable Quotes:**  
- _"ORs force the database to either merge index scans (slow) or scan the whole table (slower)."_  
- _"UNION can be a hammer, but it’s not always the right nail—watch for duplicates!"_  
- _"Postgres 17’s `BitmapOr` helps, but you still need to check the execution plan."_  

### **Conclusion:**  
Avoid `OR` clauses where possible, leveraging database-specific optimizations, query rewrites, and schema redesigns for better performance. Always inspect query plans (`EXPLAIN ANALYZE`) to validate improvements.
