# **Term.Everything: Run GUI Apps in Your Terminal Like Magic!**  

Ever wished you could run **any GUI application directly in your terminal**, even over SSH? Now you can—with **Term.Everything**, a mind-bending new tool that transforms your terminal into a graphical playground.  

### **Wait… What? A GUI… in the Terminal?**  
Term.Everything is a **Wayland compositor** that renders windows as **ASCII art or terminal-friendly images**, letting you run GUI applications (yes, even Firefox or a video game) inside your terminal. Think of it as **WSL meets X forwarding, but way cooler.**  

🔹 **Watch movies, browse the web, or play games**—all in monospace glory.  
🔹 **Works over SSH!** No more fiddling with X11 forwarding; just pure terminal wizardry.  
🔹 **Adjustable resolution**—run in low-res ASCII mode for speed or high-res for crisp images (if your terminal supports it).  

### **See It in Action**  
- **Terminal in a Terminal in a Terminal…** It's *terminals all the way down.*  
- **"I opened Firefox in iTerm2 over SSH on Ubuntu… and it just worked!"**  
- **Rendered a full movie (*Wing It!*) in ASCII, tweaking resolution for optimal clarity.**  

### **How? Why?**  
The creator wrote **a detailed breakdown** in **[HowIDidIt.md](https://github.com/mmulet/term.everything/blob/main/HowIDidIt.md)**, explaining the **black magic of Wayland compositors** and how they hacked this together with **TypeScript, a dash of C++, and sheer willpower.**

This is still early-stage software (**"Term some things" is the current milestone**), so bugs are expected. If you run into issues, **report them!**

### **E-Paper Just Got Fast: New Open-Source Display Hits 75 Hz, Rivaling LCD Speeds**  

For years, e-paper displays like those in e-readers have been celebrated for their low power consumption and paper-like readability—but suffer from painfully slow refresh rates, often below 10 Hz. Now, Modos, a small open-hardware startup, has shattered that limitation, unveiling an **e-paper display that refreshes at 75 Hz**—putting it in the same league as basic LCD monitors.  

#### **From 10 Hz to 75 Hz: A Speed Revolution**  
Most e-paper screens struggle with refresh rates under 10 Hz, making animations and video playback nearly impossible. Modos’ **open-source FPGA-based controller** overcomes this with a fast enough refresh for smooth scrolling, low-latency typing, and even basic video playback. For context:  
- **Standard e-paper**: ~1-10 Hz (sometimes *seconds* per refresh).  
- **Current fast e-paper (E Ink’s 60 Hz models)**: Still rare and expensive.  
- **Modos’ breakthrough**: 75 Hz, matching budget LCD screens.  

#### **An Open-Source Approach**  
Instead of locking down the tech, Modos has **open-sourced its controller**, allowing tinkerers to tweak the system for different panels. The startup is crowdfunding a **Dev Kit ($349+)** that includes:  
- A **13.3-inch 1600×1200** or **6-inch 1448×1072** e-paper display.  
- An **FPGA controller** with adaptable firmware.  
- Compatibility with other e-paper panels.  

“Our challenge has been showing people… e-paper can be *very* fast,” says co-founder Alexander Soto.  

#### **Why It Matters**  
Faster e-paper opens doors for:  
✅ **Eye-friendly monitors** that don’t strain users during long sessions.  
✅ **Ultra-low-power digital signage** with smooth animations.  
✅ **Future e-readers** with seamless scrolling and note-taking.  

While still not as fluid as OLED or high-refresh LCDs, **75 Hz e-paper is a game-changer**—proving that paper-like displays *don’t* have to be sluggish.

# **"We All Dodged a Bullet" – A Close Call with an NPM Supply Chain Attack**  

### **The Near-Disaster**  
Yesterday, several *extremely popular* NPM packages were compromised in a sophisticated attack. The affected libraries included innocuous utilities like:  
- Terminal text formatting  
- Color name-to-RGB mapping  
- Debugging decorators  
- Array-like value checks  

These dependencies are *everywhere*, silently lurking in countless production deployments. Had the malware been more insidious—say, an OpenAI API key stealer or an AWS credential snatcher—the fallout would have been catastrophic.  

### **The 10/10 Phishing Attack**  
The breach stemmed from a **flawless** phishing email:  
✅ **Personalized** with the target’s NPM username.  
✅ **Plausible pretext** ("Update 2FA for security reasons").  
✅ **Urgent deadline** to induce panic.  
✅ **Barely-suspicious domain** (`npmjs.help` instead of `npmjs.com`).  

Even the author admits: *"I'd probably fall for this if it hit me at the right time."*  

### **What Saved Us?**  
The malware only hijacked cryptocurrency transactions (like MetaMask payments). **But it could’ve been so much worse.** Imagine:  
- Mass API key exfiltration.  
- Cloud service takeover.  
- A Jia Tan-level backdoor lurking in every deployment.  

The attackers *wasted* a near-perfect operation on crypto fraud—missing the jackpot of AWS keys, Slack tokens, and more.  

### **The Uncomfortable Truth**  
Every dependency is a potential Trojan horse. Yet, developers can’t scrutinize every line of transitive dependencies—ship deadlines loom too large.  

**Final Thought:** If Web3 devs weren’t the main target, how many more pipelines would’ve silently burned?

Memory safety flaws are the root cause of nearly all **high-severity exploits**. Apple’s MIE doesn’t just patch bugs—it **reinvents how memory is protected at the hardware level**, making future spyware attacks exponentially harder to execute.

While `encoding/json` has served the Go community well for over a decade, real-world usage exposed critical issues:  

✔ **Behavior Flaws:**  
   - **Invalid UTF-8** (accepted silently, risking corruption)  
   - **Duplicate JSON keys** (security hazard in APIs)  
   - **Ambiguous handling of `nil` slices/maps** (causing compatibility issues)

   - Heavy allocations in token-based parsing  

### **Meet `encoding/json/v2`**  
This new package (available experimentally in Go 1.25) aims to fix these problems with:  

✅ **Stricter, Safer Defaults** (rejects invalid UTF-8, duplicate keys)  
✅ **Better Performance** (fewer allocations, streaming support)  
✅ **More Flexible API** (better `io.Writer`/`io.Reader` integration)
