### Mise: Monorepo Tasks

#### [Submission URL](https://github.com/jdx/mise/discussions/6564) | 363 points | by [jdxcode](https://news.ycombinator.com/user?id=jdxcode) | [86 comments](https://news.ycombinator.com/item?id=45491621)

## Mise Introduces "Monorepo Tasks" to Simplify Large-Scale Project Management  

**The Problem**: Managing tasks, tools, and environments across multiple projects in a monorepo is painful. Existing solutions either lack cross-project coordination (like Taskfile) or come with heavyweight complexity (like Bazel).  

**The Solution**: Mise now offers **Monorepo Tasks**, a lightweight but powerful way to:  
- **Discover & run tasks** across projects (`mise //projects/frontend:build` or `mise //...:test`)  
- **Automatic tool inheritance** – define Node/Python versions at the root, override per-project  
- **Wildcard support** (e.g., run all builds in `/services` with `mise //services/...:build`)  
- **Consistent context** – tasks always run with their project’s tools, even from the repo root  

**How It Stacks Up**:  
- *Vs. Turborepo/Nx*: Mise is language-agnostic (works with Rust, Python, etc.).  
- *Vs. Bazel*: No need for hermetic builds—keeps simplicity while adding monorepo smarts.  
- *Vs. Taskfile*: Unified task discovery and wildcards outshine scattered configs.  

**Quick Start**:  
1. Set `experimental_monorepo_root = true` in your root `mise.toml`  
2. Add tasks per-project (e.g., `[tasks.build]` in `/apps/web`)  
3. Run anything from anywhere:  
   ```sh
   mise //apps/...:test  # Test all apps
   mise '//...:*'        # Run EVERY task (brave mode!)
   ```  

**Why It Matters**: Mise bridges the gap between simplicity (e.g., "just run my tasks") and monorepo-scale needs—without requiring a PhD in build systems.

# Building a Forth-like Language: From Tokens to a VM

**A Hacker News developer shares their journey creating a Forth-like language compiler and VM** - complete with stack visualizations!

## The Fascinating World of Forth

The project explores Forth, a stack-oriented programming language, through building:

1. A tokenizer that processes Forth code
2. A bytecode compiler that translates tokens into VM instructions
3. A virtual machine that executes the bytecode

The author explains key Forth concepts simply:
- Two stacks: data stack (main operations) and return stack (control flow)
- Words - Forth's equivalent of functions
- Variables and DO/LOOP constructs

## Under the Hood

The implementation includes elegant solutions to classic compiler problems:

**Tokenization** skips whitespace and comments while converting source into atomic tokens. Special handling distinguishes between:
- Single-character operators (like `@`)
- Multi-character identifiers (like `PRINT10`)
- Reserved keywords (like `DO` and `LOOP`)

**Bytecode Generation** skips the traditional AST step (thanks to Forth's simplicity) and directly outputs operations like:
- Stack manipulation (`dup2`, `drop`)
- Arithmetic (`add`)
- Control flow (`jmp`, `call`, `ret`)
- Variable access (`load`, `store`)

## Why This Matters

This project demonstrates how to build:
- A working compiler without overwhelming complexity
- Clear visualizations of stack operations
- A VM from scratch with understandable bytecode

The post shows that language implementation can be approachable yet powerful enough to compute Fibonacci sequences.

For those wanting to understand language internals or learn Forth's stack-based paradigm, this writeup provides both working code and conceptual clarity.

# **Mojo vs. Cython: A First Look at Converting scikit-learn Code**

### **The Promise of Mojo for Python Performance**  
Mojo—a new systems programming language from Modular—promises **Python-like syntax with C-level performance**. Many, including Hacker News commenters, speculated it could replace **Cython** for accelerating Python functions. Now, with **Mojo→Python interop** in early beta (as of release 25.4), we can finally test this idea.  

### **The Test Case: Rewriting scikit-learn’s DBSCAN Inner Loop**  
A great place to find Cython? **scikit-learn**, which uses Cython extensively for performance-critical sections. The experiment focuses on **`dbscan_inner`**, a tight loop that handles cluster labeling—short, simple, and fitting Mojo’s current 3-argument limit for Python interop.  

#### **Key Changes from Cython → Mojo**  
1. **Minimal Syntax Shifts**: The core logic stayed almost identical, thanks to Mojo’s Python-like syntax.  
2. **New Boilerplate**: Mojo requires module initialization code (handled via `PythonModuleBuilder`).  
3. **Simplified Stack Handling**: Replaced C++ `vector[intp_t]` with Mojo’s `List[Int]`.  
4. **Type Casting**: Explicitly cast neighbor indices to `Int`.  

### **The Verdict? It Just Works!**  
After minor adjustments, the Mojo version **ran flawlessly** in scikit-learn’s test suite (`pytest` passed all 30 DBSCAN tests). Surprisingly, the translation was **easier than expected**—most of the Cython logic carried over directly.  

### **Limitations & Future Potential**  
- **Early Days**: Mojo’s Python interop is still in beta (e.g., workarounds like `sys.path.insert(0, "")` are temporary).  
- **Argument Limit**: Currently, Mojo functions called from Python can’t exceed 3 arguments.  
- **Performance Comparison**: Not benchmarked yet—stay tuned for future deep dives!  

### **Why This Matters**  
If Mojo matures as hoped, it could **simplify high-performance Python extensions**, offering a smoother path than Cython or hand-written C/Rust bindings. For now, it’s a promising proof of concept—**watch this space.**
