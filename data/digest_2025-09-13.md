### Pass: Unix Password Manager

#### [Submission URL](https://www.passwordstore.org/) | 276 points | by [Bogdanp](https://news.ycombinator.com/user?id=Bogdanp) | [146 comments](https://news.ycombinator.com/item?id=45236079)

### **Unix Simplicity Meets Password Security: Introducing `pass`**  

#### **TL;DR**  
`pass` is a lightweight, command-line password manager that follows Unix philosophy—storing each password in an individual **GPG-encrypted file** within `~/.password-store/`. It integrates seamlessly with existing Unix tools, supports auto-generated passwords, Git version control, and has a thriving ecosystem of extensions and GUIs.  

---

### **Why `pass`?**  
- **No New Paradigms** – Just encrypted files in a directory. Use `cp`, `mv`, `ls`, etc.  
- **Clipboard Integration** – Copy passwords securely with `pass -c [entry]`.  
- **Git Support** – Automatic versioning of password changes.  
- **Cross-Platform** – Clients for Linux, macOS, Windows, mobile, and more.  

---

### **How It Works**  

#### **1. Basic Usage**  
- **List passwords:**  
  ```sh  
  $ pass  
  ```
  Output (organized by folders):  
  ```
  Password Store  
  ├── Email  
  │   ├── gmail.com  
  │   └── work.com  
  └── Finance  
      ├── bank.com  
      └── crypto-exchange  
  ```

- **Retrieve a password:**  
  ```sh  
  $ pass Email/gmail.com  
  ```

- **Copy to clipboard (clears after 45s):**  
  ```sh  
  $ pass -c Email/gmail.com  
  ```

#### **2. Managing Passwords**  
- **Insert a new password:**  
  ```sh  
  $ pass insert Social/twitter.com  
  ```
  
- **Generate a random password:**  
  ```sh  
  $ pass generate Social/twitter.com 20  
  ```

- **Edit in $EDITOR:**  
  ```sh  
  $ pass edit Social/twitter.com  
  ```

#### **3. Git Integration**  
- **Initialize a Git repo:**  
  ```sh  
  $ pass git init  
  $ pass git remote add origin [remote]  
  ```

Every change is automatically committed. Sync with:  
- `pass git pull`  
- `pass git push`  

---

### **Getting Started**  
#### **Installation**  
- **Debian/Ubuntu:** `sudo apt install pass`  
- **macOS (Homebrew):** `brew install pass`  
- **Windows (WSL):** Install via WSL + Linux  

#### **Initialization**  
```sh  
$ pass init "GPG_KEY_ID"  
$ pass git init  # Optional (for version control)  
```

---

### **Advanced Features**  
- **Multi-line entries:** Store API keys, security Q&As, or notes under a single password.  
- **Team Sharing:** Encrypt passwords with **multiple GPG keys** for shared access.  
- **GUI Clients:** Available for Android (Password Store), macOS (Pass for macOS), and more.  

🔗 **Git Repo & Docs:** [https://git.zx2c4.com/password-store](https://git.zx2c4.com/password-store)  

---

### **Final Thoughts**  
`pass` is perfect for terminal lovers who want a **no-nonsense**, **scriptable** password manager. It leverages strong encryption with GPG while staying fully transparent—your passwords are just files you can manage like any other.  

**Try it out and kiss bloatware goodbye!** 🔑

#### [Submission URL](https://nand2mario.github.io/posts/2025/486tang_486_on_a_credit_card_size_fpga_board/) | 192 points | by [bitbrewer](https://news.ycombinator.com/user?id=bitbrewer) | [52 comments](https://news.ycombinator.com/item?id=45232565)

# **486Tang: Bringing x86 to the Sipeed Tang FPGA for the First Time**  

A new breakthrough in retro computing has arrived—**486Tang v0.1**, a port of the ao486 MiSTer FPGA core to the **Sipeed Tang Console 138K FPGA**, is now available on GitHub. This marks the first time the ao486 x86 core has been successfully ported to a **non-Altera FPGA**, opening up possibilities for running classic PC software on more affordable FPGA hardware.  

### **The Challenge & Key Differences**  
Porting a complex x86 core meant reworking several components to fit the Tang’s architecture. Some major changes include:  

🔹 **SDRAM for Main Memory** – Unlike the MiSTer’s DDR3 setup, 486Tang uses SDRAM for the CPU, adopting a trick called **“double-pumping”** (running memory logic at 2x the CPU clock) to make up for the narrower 16-bit bus.  
🔹 **Direct SD Card Access** – The Tang doesn’t have the MiSTer’s high-speed ARM-FPGA link, so disk I/O was redesigned to work directly with SD storage.  
🔹 **Boot ROM on SD Card** – BIOS, VGA firmware, and disk info now load from the first 128KB of the SD card before booting.  

### **Debugging the Beast**  
Bringing up a full PC—CPU, BIOS, peripherals—is far more complex than retro console emulation. The solution? **Verilator-based simulation** to speed up debugging:  

✅ **BIOS Debug Output** – Port `0x8888` logs (yellow text in simulation) exposed issues immediately.  
✅ **Subsystem Tracing** – Flags like `--sound` and `--ide` helped isolate bugs.  
✅ **Bochs BIOS Disassembly** – Symbolic debugging saved hours over brute-force disassembly.  

### **Performance Tuning**  
Initial performance was sluggish (~25 MHz 386-level speed), so **optimizing critical paths** was key:  

🔧 **Reset Fan-Out Fix** – Manually replicating flaky reset nets reduced delays.  
🔧 **Instruction Fetch Fix** – Decode bottlenecks were eliminated by tweaking buffer management.

# The Perils of Thread Cancellation: How a Bold curl Feature Backfired  

**The Grand Plan:** Three weeks ago, Daniel Stenberg (curl’s lead developer) introduced `pthread_cancel` in curl 8.16.0—a clever trick to interrupt stuck DNS lookups (`getaddrinfo()`). The idea? Spin up a thread for DNS resolution, then cancel it if it takes too long. But the plan quickly unraveled…  

### **What Went Wrong?**  
DNS resolution (`getaddrinfo()`) blocks, so curl spawned a thread for it. The choices for cleanup were bad:  
- `pthread_join` → **blocks** (stalls progress).  
- `pthread_detach` → **leaks threads** (no cleanup).  
- `pthread_cancel` → seemed perfect… until it **leaked memory instead**.  

### **The Glibc Trap**  
When `getaddrinfo()` runs, it:  
1. Resolves addresses (allocates memory).  
2. Checks `/etc/gai.conf` (for sorting rules).  
3. Calls `fopen()` or `open()`—both **cancellation points**.  

If the thread dies mid-operation, **all prior allocations leak**. And since `/etc/gai.conf` is rechecked on retries, the leak could happen repeatedly—disastrous for high-volume transfers.  

### **The Fallout**  
After reports of memory leaks (#18532), digging into glibc revealed:  
- **No safe way** to cancel `getaddrinfo()` without leaks.  
- The fix? **Revert entirely**. curl 8.17.0 (#18540) removes the feature.  

### **The Painful Lesson**  
- Thread cancellation is **dangerous**—hidden system calls can doom you.  
- **Workarounds?** Use `c-ares` (async DNS), but it doesn’t fully replace glibc’s features.  
- **DNS is still a minefield.** Even after decades, it’s **hard to do right**.  

**Final Takeaway:** Sometimes, the simpler (blocking) approach is the lesser evil. Or, as Daniel puts it: *"We’d rather wait than leak."* 🔄💣

### Safe C++ proposal is not being continued

#### [Submission URL](https://sibellavia.lol/posts/2025/09/safe-c-proposal-is-not-being-continued/) | 173 points | by [charles_irl](https://news.ycombinator.com/user?id=charles_irl) | [180 comments](https://news.ycombinator.com/item?id=45234460)

# **The Quest for a Safer C++: Why "Safe C++" Failed and What’s Next**  

### **One Year Later, Safe C++ Is Officially Dead**  
A year ago, a bold proposal called *Safe C++* aimed to bring Rust-like memory safety, type safety, and thread safety to C++ through an opt-in, explicit system. The idea was to create a *safe context* within C++—marked by special qualifiers—where code would be guaranteed safe, while legacy C++ remained unchanged.  

But today, the dream of Safe C++ is officially over.  

### **Why Safe C++ Didn’t Make It**  
The proposal faced strong resistance from the C++ committee. According to Sean Baxter, one of its authors:  
> *"The Rust safety model is unpopular with the committee."*  

Instead, the committee voted to prioritize **Profiles**—a different approach to safety that imposes restrictions at compile-time but doesn’t introduce new syntax or semantics.  

### **Profiles: A More Modest (But More Likely) Path to Safety**  
Profiles operate by **constraining certain C++ usages**, enforcing rules like:  
- No raw pointers (forcing `std::unique_ptr`/`std::shared_ptr` instead)  
- Bounds checking on arrays/containers  
- Avoiding undefined behavior traps  

Unlike Safe C++, they don’t introduce new borrow-checking or lifetime analysis—instead, they act like a **linter on steroids**, enforcing best practices rather than rewriting language semantics.  

### **Why the Committee Preferred Profiles**  
1. **Backwards Compatibility** – No forced rewrites; existing code keeps working.  
2. **Simplicity** – No new syntax, just rules.  
3. **Pragmatism** – The C++ community resists adopting Rust’s model wholesale.  

### **The Trade-Off**  
Profiles are weaker than Safe C++ (no borrow checker, lifetime guarantees), but they’re politically easier to standardize. As Baxter put it:  
> *"Profiles won the argument. All effort should go into getting Profile’s language for eliminating use-after-free bugs, data races, deadlocks, and resource leaks into the Standard."*  

### **The Big Question: Will This Be Enough?**  
Profiles may not eliminate all safety issues, but they’re a **step forward**—one that might actually make it into C++26. For those wanting full Rust-like guarantees, the answer remains simple: **just use Rust.**
