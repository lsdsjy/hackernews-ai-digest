# Go Struct Embedding: A Hidden Gotcha  

**The Problem with Invisible Ambiguity in Go's Struct Embedding**  

Go's struct embedding is a convenient feature for type composition, but it can lead to subtle and potentially dangerous behavior when field names collide.  

### The Basics:  
```go
type Position struct { X int; Y int }
type Rectangle struct { Position; Width int }

// Both work:
fmt.Println(rect.X)          // Promoted field from Position
fmt.Println(rect.Position.X) // Explicit access
```  
This feels intuitive—until it isn't.  

### The Landmine:  
```go
type Options struct {
  FooService      // Has URL field
  BarService      // Also has URL field (embedded via BarConnectionOptions)
}

opts := Options{...}
fmt.Println(opts.URL) // Surprise! Prints "abc.com"
```  
Even though both `FooService` and `BarService` have a `URL` field, Go silently resolves the ambiguity by choosing the "least nested" field (`FooService.URL`). No compile error. No warning.  

### Why This Matters:  
- **Bugs slip through**: This compiles and works—until a future refactor changes the field order.  
- **Undermines explicitness**: Go prides itself on clarity, but here it prioritizes convenience over safety.  
- **Testing saved the day**: The original issue was caught in tests, but not all projects have robust test coverage.  

### The Fix:  
Avoid embedding structs with overlapping field names, or explicitly qualify fields:  
```go
fmt.Println(opts.FooService.URL) // Clear intent
```  

**Lesson**: Struct embedding is powerful, but always verify field resolution behavior—especially in large codebases.

### Summary of the Discussion:  

**1. The Problem with Ambiguity in Struct Embedding**  
Many commenters agreed that Go’s struct embedding can be confusing when field names collide, as the compiler silently prioritizes the "least nested" field instead of raising an error. Some argued this violates Go's principle of explicitness and can lead to subtle bugs. However, others pointed out this behavior is documented in the spec (shallowest depth wins) and is consistent, albeit unintuitive.  

**2. Workarounds and Best Practices**  
- **Explicit Qualification**  (e.g., `opts.FooService.URL`) was the most suggested fix.  
- **Avoid Embedding Structs with Overlapping Fields**: Several commenters noted they now avoid embedding entirely or only do so for trivial cases.  
- **Use Linters/IDEs**: Tools like `gopls` or IDE warnings can help catch these issues early.  

**3. Compiler Design Choices**  
- The compiler resolves ambiguities via a depth-first search, prioritizing shallow fields. Some questioned why this wasn’t a compile-time error (like conflicting method names in interfaces).  
- A few noted this trade-off exists for convenience in composition, but conceded it’s a footgun in large codebases.  

**4. Real-World Pitfalls**  
- Embedding structs from external libraries was flagged as particularly risky—changes in dependency field names can break code silently if tests don’t catch it.  
- Some shared anecdotes where refactoring embedded structs led to runtime panics due to unexpected field resolution.  

**5. Alternative Patterns**  
- **Explicit Wrapper Structs**: Instead of embedding, some prefer flat structs with manual delegation.  
- **Interfaces for Abstraction**: Use interfaces to define required behavior without embedding.  

**6. Philosophical Divide**  
- **"Go is Explicit" Camp**: Felt the current behavior undermines Go’s clarity.  
- **"It’s a Trade-off" Camp**: Argued that embedding is optional, and developers should understand its quirks before using it heavily.  

**Notable Quote**:  
> *"Go’s struct embedding is like a chainsaw: powerful but dangerous if you don’t respect it."*  

**Final Takeaway**:  
While struct embedding is useful, its ambiguity with colliding fields demands caution—explicit qualification and testing are key. Many experienced devs recommended limiting its use to avoid surprises.

### **Tiny JSON Parser in Just 150 Lines of C Code**  

For developers who love minimalism, **sj.h** by **rxi** is a brilliantly compact JSON parsing library written in C99. With zero allocations and around 150 lines of code, it’s a lightweight alternative to bloated parsers.  

🔹 **Key Features:**  
✔ **Zero allocations** – Minimal runtime overhead  
✔ **Error messages** with precise line:column locations  
✔ **No built-in parsing for numbers/strings** – Use `strtod`, `atoi`, or custom handling  
✔ **Super tiny** (~150 LOC) yet fully functional  

📌 **How It Works**  
The library provides a simple reader-based API. Here’s how you might parse a rectangle from JSON:  

```c
typedef struct { int x, y, w, h; } Rect;
char *json = "{ \"x\": 10, \"y\": 20, \"w\": 30, \"h\": 40 }";

int main() {
    sj_Reader r = sj_reader(json, strlen(json));
    sj_Value obj = sj_read(&r);
    Rect rect = {0};
    sj_Value key, val;
    
    while (sj_iter_object(&r, obj, &key, &val)) {
        if (eq(key, "x")) rect.x = atoi(val.start);
        if (eq(key, "y")) rect.y = atoi(val.start);
        if (eq(key, "w")) rect.w = atoi(val.start);
        if (eq(key, "h")) rect.h = atoi(val.start);
    }
    printf("Rect: { %d, %d, %d, %d }\n", rect.x, rect.y, rect.w, rect.h);
}
```

🚀 **Why Use It?**  
- Perfect for embedded systems  
- No dependencies  
- Public domain (**Unlicense**) – use it freely

### The Quirkily Named Git Helper: A Tool for Taming Chaotic Commit Histories  

Mark Dominus (also known as 陶敏修) is looking for help naming his latest Git utility—currently called *what-changed-twice* (or *Fred* as a placeholder). This tool helps him clean up messy commit histories where files are modified multiple times across different commits, a common occurrence in his workflow.  

#### What’s the Problem?  
When working on multiple changes over time, commit histories can look like a chaotic jumble:  
- Fixes, WIPs, spelling corrections, and new content intermingle.  
- A single file might be modified in several commits, making it hard to track related changes.  

For example:  
```plaintext  
470947ff minor corrections  
d630bf32 continue work on `jq` series  
c24b8b24 wip  
f4695e97 fix link  
a8aa1a5c sp  (spelling fix)  
...  
```  

Separating and organizing these changes manually is tedious.  

#### Enter *Fred* (or Whatever It Should Be Called)  
The utility scans Git logs, identifies files modified in **multiple** commits, and presents a concise report:  

```plaintext  
calendar/seasons.blog  196 40 d1  
math/centrifuge.blog  193 33  
misc/straight-men.blog  53 b5 bd  
...  

196 → 196e749  
40  → 40c52f4  
d1  → d142598  
...  
```  

This helps Mark:  
1. **Spot overlaps**: Files changed in multiple commits.  
2. **Squash wisely**: Group related changes (e.g., a typo fix into the original commit).  
3. **Avoid rebase conflicts**: Commits *not* listed can be reordered safely.  

Written in Perl (despite his recent Python preference), the tool is simple yet powerful—but it’s stuck with a clunky name.  

#### What Should It Be Called?

# AI Coding Assistants: From Magic to Modern-Day Dial-Up Frustrations  

### Key Takeaways:  
- **The novelty is wearing off**: AI coding tools like Claude Code have quickly gone from feeling "magical" to frustratingly slow, reminiscent of dial-up internet in the 90s.  
- **Reliability woes**: Major AI providers (Anthropic, OpenAI, Google) are struggling with stability—OpenRouter’s (albeit limited) data shows frequent outages and retries.  
- **The token explosion**: AI token usage is skyrocketing, with agentic workflows consuming **1,000x more tokens** than standard chat queries—straining infrastructure like early broadband ISPs.  
- **Speed matters**: Current models run at 30-60 tokens/second (tok/s), feeling sluggish for real-time coding. Faster models (2,000+ tok/s, like Cerebras Code) hint at a future where the bottleneck shifts from AI to human cognition.  
- **The next leap**: The holy grail is **parallel unsupervised agents**—multiple AI attempts at a task, ranked automatically—but today’s speed and context limitations hold this back.  
- **Infinite demand loop**: Better AI doesn’t mean *less* usage—it means *new* workflows that devour even more resources. Unlike the 2000s telecom crash, demand shows no sign of plateauing.  

### The Big Question:  
Will AI infrastructure scale fast enough to keep up—or will semiconductor stagnation throttle progress?
