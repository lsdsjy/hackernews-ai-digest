### Making a font of my handwriting

#### [Submission URL](https://chameth.com/making-a-font-of-my-handwriting/) | 303 points | by [kickofline](https://news.ycombinator.com/user?id=kickofline) | [70 comments](https://news.ycombinator.com/item?id=45141636)

**Handwritten Fonts & the Frustration of DIY: A Hacker’s Battle Against FontForge**  

Building a personal website that *feels* personal is an art—one that often clashes with the sterile, corporate vibes dominating the web today. One developer set out to inject more personality into their site by ditching generic monospace fonts and opting for a custom, handwritten style.  

### **The Dream: Crafting a Handwritten Font**  
The idea was simple: create a script-like font that mimics natural handwriting. The execution? Less so.  

#### **The Open-Source Struggle**  
The plan involved:  
1. Drawing glyphs in **Inkscape** (open-source vector tool).  
2. Importing them into **FontForge** (open-source font editor).  

But FontForge lived up to its reputation for frustration:  
- Crashed when closing an unwanted dialog.  
- Hidden "New" button in an "Open Font" prompt.  
- A baffling import process that rejected files without clear feedback.  
- A clunky, non-standard UI that made even basic tasks feel like wrestling with duct-taped software.  

After rage-quitting, they explored **Inkscape’s SVG font tools**, but merging paths for multi-stroke letters proved tedious.  

### **The Closed-Source Savior: Calligraphr**  
In desperation, they turned to **Calligraphr**—a paid but frictionless alternative. For a one-time £8 fee (no forced subscriptions!), it offered:  
- Printable templates to hand-draw letters.  
- Smart scanning and auto-alignment.  
- A far smoother workflow.  

**Result?** A custom font that *actually* felt personal—without hours of UI-induced suffering.  

### **Lessons Learned**  
- **Sometimes, open-source UX fails you**—when a tool fights you more than it helps, the cost-benefit shifts.  
- **Paid tools don’t always mean subscriptions**—one-time payments can be fair and transparent.  
- **Handmade touches make the web warmer**—even if the process involves a few rage-quits along the way.  

Would they brave FontForge again? Probably not anytime soon. But at least their website now has that quirky, human touch—mission accomplished.

### Protobuffers Are Wrong (2018)

#### [Submission URL](https://reasonablypolymorphic.com/blog/protos-are-wrong/) | 184 points | by [b-man](https://news.ycombinator.com/user?id=b-man) | [228 comments](https://news.ycombinator.com/item?id=45139656)

# **Why Protobuffers Are Flawed by Design**  

### **A Rant Against Google’s Protocol Buffers**  

**Author:** A former Google engineer  
**Verdict:** Protobuffers are poorly designed, ad-hoc, and full of arbitrary restrictions that make them a nightmare to work with.  

### **The Core Issues**  

1. **"Built by Amateurs" (Even Though It’s Google)**  
   - Disregard the usual defense that “Google employs genius engineers.” The author, who worked there, says Protobuffers are riddled with questionable design choices.  
   - The type system is exceptionally bad—too rigid in some ways, too loose in others, and generally unsophisticated.  

2. **Ad-Hoc, Inconsistent Features**  
   - Many limitations seem arbitrary:  
     - `oneof` fields **can’t** be `repeated`.  
     - `map<k,v>` fields support special key-value syntax, but user-defined types **can’t** use it.  
     - Map keys **can’t** be `bytes` or enums (even though enums are just integers everywhere else).  
     - `map` fields **can’t** be repeated.  
     - `map` values **can’t** be other maps.  
   - This mess comes from tacking on poorly integrated features over time.  

3. **No Compositionality**  
   - Protobuffers fail at basic type composition.  
   - Instead of true sum (`oneof`) and product types, they use hacky transformations:  
     - `oneof` gets desugared into **mutually exclusive optional fields** (which breaks if you could make them `repeated`).  
     - `map<k,v>` is secretly `repeated Pair<k,v>`, but `repeated` itself is a keyword, not a type, so it **can’t be nested**.  

### **How It *Should* Work**  
A better design would:  
1. **Make all fields required** (messages become pure product types).  
2. **Promote `oneof` to proper sum types**.  
3. **Allow parameterized types**.  

With these:  
- **Optional fields?** Could be modeled as:  
  ```protobuf  
  coproduct Optional<t> {  
    t value = 0;  
    Unit unset = 1;  
  }  
  ```  
- **Lists?** Just a recursive type:  
  ```protobuf  
  coproduct List<t> {  
    Unit empty = 0;  
    Pair<t, List<t>> cons = 1;  
  }  
  ```  
(Actual serialization could still optimize this under the hood—implementation ≠ semantics.)  

### **The Scalar vs. Message Nightmare**  
- **Scalar types (`int32`, `bool`, `string`)** are **always present, **initialized to defaults (`0`, `false`, `""`).  
- **Message types** behave differently.  
- **The problem?** You **can’t differentiate** between an explicitly set default value and an **unset** field!  
- **Why?** Allegedly, it lets protobuffers skip sending default values over the wire (but the docs don’t even confirm this).  

This makes **forward/backward compatibility** a headache—if `0` is a valid value, how do you know it wasn’t just omitted?  

### **Final Thoughts**  
Protobuffers succeed **despite** their design, not because of it. They’re full of arbitrary restrictions, awkward semantics, and half-baked ideas—proof that even Google engineers sometimes build flawed tools.  

Would a principled redesign fix this? **Yes.** Will it happen? Probably not.  

**The real question:** *Why can’t enums be map keys?* (Nobody knows.)
