**Solar-Powered Blog on a Recycled Google Pixel 5? Yes, It’s Possible!**  

In an era of hyperscale cloud servers and energy-hungry data centers, one Android enthusiast decided to take a different route—hosting a blog entirely on a **recycled Google Pixel 5**… powered by solar energy.  

### **The Inspiration & Hardware**  
After stumbling upon posts from fellow tinkerers running websites on **microcontrollers, Android phones, and even OpenWRT routers**, the idea was born. The chosen device? A carrier-locked **Google Pixel 5**, donated by a brother-in-law. While Verizon’s bootloader lock prevented installing custom Linux distros (*goodbye, PostmarketOS dreams*), the Pixel 5’s **USB-OTG and Ethernet dock support** made it perfect for a wired internet connection.  

### **Going Off-Grid**  
Not satisfied with just using old hardware, the blogger paired the phone with:  
✔ A **100W solar panel** (from Harbor Freight)  
✔ A **Jackery 160W power station** (also serving as a mobile charging hub)  
Result? A **fully off-grid, solar-powered blog**—living the permacomputing dream.  

### **How It Works: Termux to the Rescue**  
Instead of overcomplicating things with a full Linux proot setup, the blog runs on **Termux**, a powerhouse terminal emulator for Android. Key packages installed:  
- **Hugo** (static site generator, already in Termux repos since 2018!)  
- **OpenSSH, Git, Cronie** (for remote management)  
- **Dufs** (for easy file uploads via browser)  

The setup was surprisingly simple:  
1. Install Hugo & dependencies via Termux.  
2. Enable SSH (*port 8022—non-negotiable*) with `sv-enable sshd`.  
3. Deploy and serve the site, routing through an existing reverse proxy.  

**Performance? Flawless.** “*Nobody can tell it’s running on a phone instead of a VPS,*” the blogger notes.  

### **Would You Try This?**  
If you love **low-power computing, recycling old tech, or just unconventional server setups**, this project is a goldmine. The blogger is open to sharing deeper guides—ping them on Mastodon if you want a full walkthrough!

# **The Clever Trick to Make Your Home Server Sleep When Idle and Wake On Demand**  

### **The Problem:**  
You’ve got a home server running Ubuntu, mostly for Time Machine backups, but it’s chugging power 24/7 when most of the time... it’s doing nothing. Wouldn’t it be great if it could **sleep when idle and wake up only when needed**—just like a desktop PC?  

**Turns out, that’s harder than it sounds.**  

### **The Solution:**  
A clever setup combining Wake-on-LAN (WoL), ARP spoofing, and a tiny always-on helper (like a Raspberry Pi) to trick your network into thinking the server is awake when it’s not.  

### **How It Works:**  
1. **Server Side:**  
   - **Sleeps automatically** when idle (no SSH users, no active AFP connections).  
   - **Wakes up** when another device (like your Mac) tries to access it.  
   - **Disabled IPv6** (since we rely on ARP, an IPv4 thing).  

2. **Helper Device Side (Raspberry Pi):**  
   - **Acts as an "ARP stand-in"**—responding to network requests *as if it were the sleeping server*.  
   - **Triggers Wake-on-LAN** when needed, using **unicast packets** (not just magic packets).  

### **The Key Ingredients:**  
✅ **A low-power "always-on" device** (like a Pi) to handle wake-up duties.  
✅ **A server with Wake-on-LAN (WoL) support**—configured for **unicast** wake-ups, not just magic packets.  
✅ **A simple Ruby script** on the Pi to impersonate the server via ARP.  

### **Why This Is Cool:**  
- **Massive power savings**—your beefy server only runs when truly needed.  
- **No manual intervention**—Time Machine backups, SSH, and other services just work.  
- **Surprisingly simple** once set up (though getting there took some trial and error).  

### **Gotchas to Watch For:**  
⚠️ Your server’s NIC **must support unicast WoL** (not all do).  
⚠️ **Disable IPv6**—this trick relies on IPv4 ARP.  
⚠️ **Stray network traffic** (like random pings) could accidentally wake the server.

# 🔍 Hacker News Digest: The Hidden Power of HTML's `<template>` Element  

### **Key Takeaways:**  
- The `<template>` element in HTML is a powerful but often overlooked tool for holding reusable DOM fragments that aren't rendered immediately.  
- It’s widely supported (since 2015!) and works by storing inert HTML that can be cloned and injected into the DOM via JavaScript.  
- Newer features like **declarative Shadow DOM** (via `shadowrootmode`) allow shadow roots to be created directly in HTML, rivaling `Element.attachShadow()`.  

### **How It Works:**  
📌 **No Content, No Problem**:  
- Nested HTML inside `<template>` doesn’t become part of active DOM—instead, it’s stored in a **`DocumentFragment`** accessible via `.content`.  
- Trying to append children directly to `<template>` breaks its structure.  

🎭 **Shadow DOM Integration**:  
- With **`shadowrootmode="open"`** or **`"closed"`,** the parser converts a `<template>` into a shadow root *declaratively* (no JS needed!).  
- Other useful attributes:  
  - `shadowrootdelegatesfocus`: Automatically delegates focus to the first focusable element.  
  - `shadowrootclonable`: Ensures clones of the host element include the shadow root.  

### **Real-World Example:**  
```html
<template id="productrow">
  <tr>
    <td class="record"></td>
    <td></td>
  </tr>
</template>
```  
**JavaScript usage:**  
```js
if ("content" in document.createElement("template")) {
  const clone = template.content.cloneNode(true); // 🔄 Deep clone
  document.querySelector("tbody").appendChild(clone);
}
```  

🤯 **Gotchas:**  
- `<template>` ignores `<html>`, `<head>`, and `<body>` tags inside it.  
- Declarative shadow roots only work for the first `<template>` with `shadowrootmode` in its parent.  

🔗 **Why It Matters:**  
- Reduces repetitive DOM manipulation.  
- Enables cleaner, more maintainable HTML-in-JS patterns.  
- Modern declarative Shadow DOM makes web components more powerful.  

💡 **Final Thought:** `<template>` is like a Swiss Army knife for dynamic HTML—underutilized but incredibly handy for templating and shadow DOM magic!

### Indices, not Pointers

#### [Submission URL](https://joegm.github.io/blog/indices-not-pointers/) | 86 points | by [vitalnodo](https://news.ycombinator.com/user?id=vitalnodo) | [56 comments](https://news.ycombinator.com/item?id=45110386)

### **The Power of Indices Over Pointers: A Simple Trick for Faster, Leaner Data Structures**  

Have you ever thought about how the way you store nodes in a tree or linked structure impacts performance? If you're allocating memory for each node individually ("the nest of pointers" approach), you might be missing out on a game-changing optimization: **use indices, not pointers.**  

#### **Why Indices?**  
Instead of scattering nodes across memory with `malloc` or `new`, store them in a **contiguous array** (like a dynamic array). Each node then references others via **indices** (array positions) rather than pointers.  

#### **Benefits You Can’t Ignore**  
✅ **Smaller Nodes** – A 32-bit index (a `u32`) is half the size of a 64-bit pointer—great if you’re not storing billions of nodes.  
✅ **Faster Access** – Contiguous memory means better cache locality, fewer cache misses, and faster traversal.  
✅ **Fewer Allocations** – A single dynamic array grows in chunks (e.g., doubling capacity), drastically reducing allocation overhead compared to individual `malloc`s.  
✅ **Instant Frees** – Freeing the entire structure is **one operation** (`free(array)`) instead of recursive pointer chasing.  

#### **The Catch: Individual Deletion is Harder**  
If you need to delete single nodes in constant time, you’ll need:  
- A **freelist** (stack of unused indices) to reuse gaps.  
- Or, accept that deletions require O(n) shifting (fine if bulk operations dominate).  

#### **Zig Example: Less Code, More Speed**  
Zig makes this pattern elegant, using **enums for type-safe indices** and passing allocators explicitly. Here’s a taste:  

```zig  
var tree = Tree{
    .nodes = ArrayList(Node).init(allocator),
};

const root = try tree.createNode(45);  
const left = try tree.createNode(10);  
tree.setLeftChild(root, left); // Uses indices, not pointers!  
```  

#### **When Should You Use This?**  
- **ASTs, game scenes, graphs**. If you rarely delete nodes piecemeal, this is a no-brainer.  
- **Performance-sensitive code**. The cache wins alone can make traversal **3-10x faster**.

### **Key Themes from the Discussion**  

1. **Pointers vs. Indices Trade-offs**  
   - **Pros of Indices**: Smaller size (32-bit vs. 64-bit pointers), better cache locality, fewer allocations, and easier serialization.  
   - **Cons of Indices**:  
     - Extra bounds checks (though modern CPUs handle this efficiently).  
     - Thread-safety concerns (ABA problems, stale indices if underlying memory reallocates).  
     - Can't replace pointers in all cases (e.g., shared memory across processes).  

2. **Rust-Specific Debates**  
   - Some argue indices bypass Rust’s borrow checker, risking dangling indices. Others counter that indices are memory-safe if managed properly (e.g., typestate or arena allocators).  
   - **`rustc` compiler itself uses indices extensively**, proving the pattern’s viability in safe code.  

3. **Historical and Architectural Context**  
   - Similar to FORTRAN’s pre-allocated work arrays or DOS-era `NEAR` pointers in segmented memory.  
   - ECS (Entity-Component-System) in game engines popularized the "array of structs" approach.  

4. **Performance Nuances**  
   - Indices excel in contiguous arrays but lose edge if nodes scatter (defeating cache locality).  
   - **32-bit indices** often suffice, with ARM/Android even optimizing tagged pointers for this.  

5. **Language Support**  
   - Zig’s explicitness (e.g., `ArrayList` + manual allocators) makes this pattern elegant.  
   - C/C++ can achieve similar gains with custom allocators or slabs.
